# Lab Sheet Reader

**손으로 적은 시험 기록지를 읽어서, 값이 말이 되는지 스스로 검증하고, 업무용 엑셀에 붙여넣을 형태로 내보내는 도구.**

```bash
npm run read -- samples/일지.jpg     # → out/결과.xlsx
```

> **결론 —** 기술적으로는 됐고, 실제로는 쓰이지 않는다.
> 만들고 나서 이 업무를 하는 분께 여쭤보니 이미 나름의 방식이 있었다.
> **순서를 틀렸다.** 아래는 무엇을 만들었고 무엇을 확인했는지의 기록이다.

---

## 1. 무슨 문제였나

공공 시험기관에서 수질 검사 결과를 정보시스템에 등록한다.
그런데 값이 나오는 곳과 들어가는 곳 사이에 **종이가 하나 끼어 있다.**

```text
시험 기기 → (인터넷·USB 차단된 PC) → 인쇄 → 사람이 보고 손으로 입력
손글씨 일지 →                                 ↑
                                    여기서만 오타가 난다
```

완벽한 디지털 데이터가 종이와 사람 손을 거쳐 다시 디지털이 된다.
이 구간을 카메라로 대신할 수 있는지 확인해보려 했다.

## 2. 만든 것


## 4. 어려웠던 것과 푼 방법

### ① 정답지가 없는 상태에서 판독을 검증하기

시스템에 입력하기 **전**에 검증해야 하는데, 그 시점에는 대조할 상대가 없다.
성적서도 기록부도 입력이 끝나야 나온다.

**기기 출력물에 이미 정답이 섞여 있다는 것**을 발견해서 풀었다.
실험실은 기기가 제대로 도는지 보려고 답을 아는 시료를 같이 넣는다.
세척수는 0 근처, 표준품은 알려진 농도 근처여야 한다.

```text
표준품 STRE(5) 자리에서  5.171  이 읽혔다   →  정렬이 맞다
                       0.05135 가 읽혔다   →  표가 한 줄 밀렸다
```

> **이렇게 설명하면 된다**
> OCR은 표에서 행이 밀려 읽히는 사고가 나는데, 값은 전부 정상 범위라
> 어떤 검증 규칙에도 안 걸립니다. 그래서 실험 배치에 원래 들어있는
> QC 시료를 앵커로 썼습니다. 블랭크는 0 근처, 표준품은 알려진 농도 근처여야
> 하니까 그 자리 값을 보면 정렬이 맞는지 즉시 판정됩니다.
> 외부 대조 자료 없이 판독 결과를 자기 검증하는 구조입니다.

손글씨 일지에는 QC 시료가 없다. 대신 **뒤집힐 수 없는 물리 관계**를 썼다.

```text
D1 > D2         용존산소는 배양하면 줄어든다
여지 후 > 전     부유물이 쌓이면 무거워진다
```

이것으로 실제 오독 두 개를 잡았다 (`시료량 9.25`, `D1 < D2`).

다만 한계가 분명하다. **이것으로 "맞다"는 알 수 없고 "가능하다"만 안다.**
`8.97` 을 `89.7` 로 읽으면 걸리지만 `8.91` 로 읽으면 안 걸린다.

### ② 정확도보다 헛경보를 줄이는 것이 중요했다

정기시료만 보고 규칙을 만들었더니 민원시료에서 **헛경보가 20건** 났다.
BOD 시료량이 100mL 인 것도 정상인데 "300이 아니다"라고 걸었다.

```text
열 번 중 여덟 번이 헛짚으면  →  세 번째부터 아무도 안 본다
```

정해진 값 목록 대신 범위로 바꾸니 **0건**이 되었다.

> **이렇게 설명하면 된다**
> 재현율보다 정밀도를 택했습니다. 몇 개 놓치더라도 "얘가 말하면 진짜다"가
> 되는 편이, 자주 알리면서 대부분 헛짚는 것보다 낫습니다.
> 경고가 잦으면 그 기능 자체가 무시당하니까요.

### ③ 병목이 어디인지 재서 찾았다

문서 한 장에 3분 34초가 걸렸다. 토큰을 나눠 재보니 답보다 **생각(thinking) 토큰이 네 배** 컸다.

| | 시간 | 출력 토큰 | 결과 |
|---|---|---|---|
| 기본값 | 3분 34초 | 12,211 | — |
| thinking LOW | **1분 32초** | **2,625** | 동일 |

표를 읽는 일은 추론이 아니라 보고 옮기는 일이라 생각이 별로 필요 없었다.
**2배 빠르고 4배 싸졌다.**

### ④ 확장을 코드가 아니라 데이터로

문서 양식은 계속 늘어난다. 과가 대여섯 개 더 있고 기기도 다르다.
판별 조건 · 열 정의 · 지시문 · 검증 규칙을 **전부 JSON에** 두었다.

```json
{
  "id": "toc-result",
  "detect": { "allOf": ["NPOC", "Manual Dilu"] },
  "qc": [{ "match": "^STRE", "expect": { "near": 5, "tol": 0.5 } }]
}
```

새 기기가 들어오면 파일 하나 추가로 끝나고 코드는 건드리지 않는다.
함수를 넣지 않은 것은 나중에 화면에서 등록할 수 있게 하기 위해서다.

## 6. 왜 멈췄나

만든 뒤 실제로 이 업무를 하는 분께 여쭤봤다. 이미 값을 한 번 넣으면
보고서와 필요한 형태가 따라 나오게 엑셀을 짜두셨다고 했다.
그리고 그다음 말이 더 정확한 이유였다.

> 한 번만 입력하면 되니까 그렇게 불편하지는 않다. 매번 하는 일이니.

자동화된 것은 **입력 이후**다. 최초 입력은 여전히 손으로 한다.
다만 그것이 매일 하는 일이라 **불편으로 인식되지 않는다.**

이 도구가 없애려던 것이 바로 그 최초 입력이었다. 기술적으로는 없앨 수
있었지만, **없애야 할 만큼 아픈 곳이 아니었다.**

```text
있는 불편        ≠        느끼는 불편
```

익숙해진 불편은 불편으로 세어지지 않는다. 그래서 불편의 크기를
당사자에게 직접 물으면 과소평가된다. "뭐가 불편하세요"에 "별로요"라는
답이 나오는 이유가 이것이다.

화면을 만들지 않은 것은 의도적이다. 쓰이지 않을 것을 알고 나서
두 주를 더 쓸 이유가 없었다.

## 7. 다시 한다면

```text
1  이 업무를 하는 사람에게 먼저 묻는다
     "어제 하루 뭐 하셨어요"      구체적 행동을 묻는다
     "최근에 다시 한 일이 뭐예요"  재작업은 낭비의 신호다
     "쓰시겠어요" 는 소용없다      늘 "쓰죠" 라고 답하신다

2  이미 어떻게 하고 계신지부터 본다
     자동화되어 있을 수 있다. 대개 그렇다
     그리고 말보다 옆에서 보는 게 정확하다

3  그다음에 만든다
```

기술이 아니라 **순서를 틀렸다.**

다만 빈손으로 "뭐가 불편하세요"를 묻는 것보다 돌아가는 것을 들고 간 것은
나쁘지 않았다. 물어볼 명분이 되었고, 답도 구체적으로 돌아왔다.
