# 쓸 기술과 고른 이유

> 무엇을 쓰는지보다 **왜 그걸 골랐는지**가 중요하다.
> 나중에 바꿀 때 이 문서를 보고 판단한다.

---

## 확정

```text
Next.js (App Router)   화면과 서버를 한 프로젝트에
TypeScript             타입 검사
Tailwind               스타일
Gemini API             판독.  개발 단계.  나중에 갈아끼운다
pdfjs-dist             PDF 를 화면에 그리고 조각을 잘라낸다
Cloudflare Workers     배포
```

### 판독 API 를 Gemini 로 시작하는 이유

돈 때문이다. 그리고 성능으로도 나쁘지 않다.

```text
개발 단계   Gemini 무료 티어 + 시료명 가린 스캔본      0원
실사용      유료 티어로 전환.  또는 다른 회사로
```

**무료 티어는 보낸 내용을 학습에 쓴다.** 사람이 검토할 수도 있다.
그래서 개발할 때는 **시료명 열을 검게 칠한 스캔본**만 쓴다.
어차피 판독에서 어려운 건 숫자지 이름이 아니다.

무료 한도는 개발에 충분하다.

```text
Gemini 2.5 Flash   10 RPM · 하루 500회     뭉치 하나에 7회쯤 부르니 하루 70뭉치
Gemini 2.5 Pro     5 RPM · 하루 25회       정확도 비교할 때만
```

손글씨 인식 벤치마크에서 Gemini 가 상위였다. 영어 전용 시험이었지만
이 문서에서 손으로 쓴 것은 대부분 숫자라 그 결과가 꽤 들어맞는다.

### 반드시 갈아끼울 수 있게 만든다

```text
lib/reader/
├── index.ts       공통 인터페이스 — 나머지 코드는 이것만 안다
├── gemini.ts
├── openai.ts      나중에
└── anthropic.ts   나중에
```

**나머지 코드는 어느 회사 API 인지 몰라야 한다.** 파일 하나 추가하면
후보가 늘어나고, 그러면 뒤에 적은 비교 실험이 설정 한 줄이 된다.

### 보안은 무료/유료가 가른다

```text
전송 중      셋 다 HTTPS.  쟁점 아님
학습 사용    유료는 셋 다 안 씀.  Gemini 무료만 쓴다
보관         남용 감시 목적으로 일정 기간 보관 후 삭제
             회사마다 다르고 자주 바뀌니 붙이기 전에 확인한다
```

기술적 보안보다 **기관 규정이 진짜 관문**이다. 다만 이 도구는
**기기 출력물만 보내고 성적서·시험기록부·공문은 보내지 않는다.**
담당자 실명과 접수번호는 그 세 문서에만 있으므로,
**설계상 개인정보가 나가지 않는다.** 설명할 때 이 점을 앞세운다.

### Next.js 를 고른 이유

API 키를 감추려면 **서버가 필요하다.** 브라우저 코드에 키를 넣으면
개발자도구로 그대로 보이고, 남이 가져다 쓰면 본인 카드로 결제된다.

그렇다고 서버를 따로 세우면 관리할 게 두 배가 된다. Next.js 는 화면과
서버 코드를 한 프로젝트에 담을 수 있어서, 판독 요청만 서버를 거치게 하면 된다.

```text
브라우저   PDF 를 화면에 그린다 · 그리드를 보여준다
서버       API 키를 들고 판독을 대신 요청한다
```

> **용어** — App Router 는 Next.js 가 폴더 구조로 주소를 정하는 방식이다.
> `app/upload/page.tsx` 파일이 `/upload` 주소가 된다.

### pdf.js 가 필요한 이유

스캔한 PDF 는 **글자가 아니라 사진 덩어리**다. 그래서 두 가지가 따로 필요하다.

```text
판독용   PDF 파일을 그대로 API 에 넘긴다.  거기서 알아서 읽는다
표시용   pdf.js 로 브라우저 화면에 그린다.  셀을 누르면 그 부분을 확대
```

표시용이 없으면 "왜 그렇게 읽었는지" 사람이 확인할 방법이 없다.
CLAUDE.md 의 네 가지 중 투명성이 여기 걸린다.

### Cloudflare Workers 를 고른 이유

같은 사람이 다른 프로젝트에서 이미 써봤고, 기관 PC에서 `workers.dev`
주소가 열리는 것을 확인했다. 무료이고 서버 장비가 필요 없다.

## API 쪽에서 쓸 기능

```text
PDF 입력            파일을 그대로 넘긴다.  이미지로 변환할 필요 없음
Structured Outputs   응답을 정해둔 JSON 형태로만 나오게 강제한다
Prompt Caching       매번 같은 지시문 부분을 싸게 처리한다
```

### Structured Outputs 가 중요한 이유

AI 는 모르는 것도 그럴듯하게 지어낸다. 시료명을 지어내면 **값이 통째로
엉뚱한 지점에 붙는다.** 그래서 답할 수 있는 후보를 미리 못 박는다.

```text
sampleName:  목록에 있는 이름 + "UNKNOWN" 중에서만
```

목록에 없는 이름은 **애초에 나올 수가 없다.** 확신이 없으면 `UNKNOWN`
을 뱉게 하고, 그건 사람이 본다. 억지로 고르게 하면 그게 곧 지어내기다.

> **용어** — 환각(hallucination)은 AI 가 사실이 아닌 것을 자신 있게
> 말하는 현상이다. 이 도구에서는 "그럴듯한 오답"이 제일 위험하다.
> 값이 전부 정상 범위라 검증 규칙에도 안 걸리기 때문이다.

## 아직 안 정한 것

### 그리드 (표 화면)

**직접 만든 `<table>` 로 시작한다.** 필요한 기능이 적기 때문이다.

```text
표 보여주기 · 셀 색칠 · 셀 누르면 원본 확대 · 범위 복사
```

엑셀의 100분의 1만 있으면 된다. 처음부터 라이브러리를 얹으면
배우는 데 시간이 더 든다. 부족해지면 그때 아래에서 고른다.

```text
TanStack Table          렌더링은 직접.  자유롭지만 손이 감
react-datasheet-grid    가볍고 엑셀 느낌
AG Grid Community       강력하지만 무겁다
```

**Handsontable 은 후보에서 뺀다.** 엑셀 유사도는 제일 높지만 상업용
라이선스가 필요하다. 업무에 쓰면 상업적 사용에 해당한다.

> 라이선스는 바뀐다. 실제로 넣기 전에 각 저장소에서 다시 확인한다.

### 테스트

`Vitest` 를 쓸 예정이다. **파서를 고칠 때 회귀 검사가 꼭 필요해진다.**

```text
스캔본을 모아두고  →  파서를 고칠 때마다 전부 다시 돌린다
                    →  뭘 망가뜨렸는지 즉시 안다
```

이건 정확도 관리의 핵심이라 미루더라도 반드시 한다.

> **용어** — 회귀(regression)는 고치다가 멀쩡하던 게 망가지는 것이다.
> 회귀 검사는 그걸 잡으려고 예전 것을 다시 돌려보는 일이다.

### 상태 관리

`useState` 로 시작한다. 화면이 하나뿐이라 아직 필요 없다.
여러 화면이 같은 값을 봐야 할 때 `Zustand` 를 검토한다.

## 안 쓰기로 한 것

```text
데이터베이스        파일을 주고받으면 끝나는 일이다.  남길 게 없다
로그인             처음에는 혼자 쓴다.  여럿이 쓸 때 다시 본다
Tesseract          무료지만 손글씨를 못 읽는다
PaddleOCR          인쇄체는 괜찮으나 표 구조를 이해하지 못한다
```

마지막 두 개가 중요하다. 일반 OCR 은 **"글자와 좌표"만 준다.**
"이 숫자가 몇 번째 시료의 어느 항목인지"는 알려주지 않는다.
그걸 직접 계산하려면 몇 주가 든다.

```text
1층   글자 읽기      "4.337" 이라는 글자가 여기 있다
2층   문서 이해      그건 14번 시료의 TOC 값이다
```

우리에게 필요한 건 2층까지다.

## 후보를 고를 때는 재본다

한글 손글씨 판독에 대한 **믿을 만한 공개 비교 자료는 없다.** 있는 것은
업체가 자기 제품을 잰 것이거나, 손글씨가 빠진 비교이거나, 영어 전용이다.

그래서 판독 서비스를 정할 때는 직접 잰다.

```text
1  실제 스캔본 20장 확보
2  정답을 손으로 작성           ← 1~2시간.  제일 귀찮지만 이게 자산이다
3  후보들에 같은 파일을 돌린다
4  세 가지를 센다
```

```text
셀 정확도       칸 단위로 몇 개나 맞췄나
정렬 오류       값이 통째로 한 줄 밀렸나        ← 가장 위험
기권율          모를 때 UNKNOWN 을 뱉었나       ← 이게 높은 쪽이 낫다
```

마지막이 중요하다. **모를 때 모른다고 하는 쪽이, 가끔 틀리면서 항상
확신하는 쪽보다 낫다.** 앞의 것은 사람이 몇 칸만 보면 되고,
뒤의 것은 전부 봐야 하기 때문이다.

이 평가 세트는 버리지 않는다. 나중에 지시문을 고치거나 모델을 바꿀 때
그대로 회귀 검사가 된다.

### 이렇게 설명하면 된다

> 손글씨 한글 OCR은 공개 벤치마크가 사실상 없습니다. 벤더 자체 발표거나
> 손글씨가 빠진 비교뿐이라, 실제 문서 20장으로 평가 세트를 만들어서
> 후보를 직접 비교했습니다. 지표는 셀 정확도만 보지 않고 행 정렬 오류와
> 기권율을 따로 쟀는데, 정렬이 밀리면 값은 전부 정상 범위라 검증에
> 안 걸려서 가장 위험하기 때문입니다. 그 평가 세트를 회귀 테스트로
> 그대로 재사용하고 있습니다.
